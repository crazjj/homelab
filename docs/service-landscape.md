# Service landscape

I have installed more tools than I still use. This is the current working set,
not a list of every container I have tried. A service stays when it solves a
recurring problem, supports one of my projects or teaches me something concrete.

| Service or group | Status | Why it is here |
| --- | --- | --- |
| Zoraxy | Running | Reverse proxy, TLS certificates and a quick view of internal uptime checks. |
| Organizr | Running | The start page I use to open services and some proxied embedded views. |
| Komodo | Running | A central view of containers, Compose stacks and updates. |
| OneDev | Running | Local repository mirrors, Gradle builds and downloadable artifacts when I want a fallback beside GitHub. |
| Nextcloud | Running | File sync and a useful example of an application whose state is more than one Compose file. |
| ArchiveBox | Running | Saving web content that I may want to find again later. |
| n8n | Running | Small automations and experiments with connecting services. |
| Guacamole | Occasional | A persistent remote desktop session when a normal SSH session is not enough. |
| Minecraft stack | Running | Hostname routing, automatic start and stop, persistent worlds and coordinated backups. |
| Borg and Vorta | Running; restore partly tested | Hourly encrypted archives. I have restored one small file, but not a complete service. |
| Steam download staging | Occasional | Downloads can run while my louder gaming PC is off, followed by a fast local transfer. |
| GNOME Boxes and remote IntelliJ | Tested | Experiments with VMs and using the homelab as a remote development machine. |

The table describes how I use the system now. Planned applications do not go
here until I have actually tried or adopted them. Exact endpoints, account names
and network details stay out of the public repository.
